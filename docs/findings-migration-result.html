Migration audit  ·  ORDERS.fmb → Vaadin Flow

What went right and wrong in the migrated app

v1→v2 proved fixes compound. The v2→v3 gap proved something scarier: the loss you never argue about in review is the one nobody noticed was gone. The question is not “how do we fix the misses we catch” — it’s how do we not miss essential features without knowing it.
v2 shipped app — S_ORD / S_ITEM spine v3 designed, never built 151 ledger rows
What “the migrated app” is. The shipped app is the v2 branch — the S_ORD / S_ITEM master-detail spine of ORDERS.fmb. v3 was designed but never built: its PRD, its disposition ledger (151 rows) and ADR-0015 exist on master, but the v3 build tickets (#85–#95) never landed — the highest ORDERS build issue in git history is #59. So throughout, v3 = the plan that catches v2’s gaps, and the ledger’s migrated-as rows citing #85–#95 describe v3’s intent, not v2’s reality.
§1 — What went right

The migrated parts are genuinely good

PL/SQL business logic → pure, tested Java

Every trigger and formula on the spine has a traceable Java counterpart, with the business rules pushed into pure Domain types (ADR-0001) that unit-test without Spring, Vaadin, or a database. The formulas quote almost 1:1 from the PL/SQL.

Architecture & concurrency — the real engineering

The substance is not the formulas (see §3.1) — it’s the plumbing, and the plumbing is solid: a whole-graph commit that validates first, writes the scn-guarded header UPDATE before anything else (so a conflict leaves the DB untouched), then diffs working vs. persisted lines into inserts/updates/deletes; a typed SaveResult (Committed / Conflict / Invalid) instead of a silent overwrite; an in-memory editing session with re-entrancy guards; and clean View ← Presenter ← Service ← Domain ← Data layering throughout.

Layout fidelity (ADR-0012 / -0013)

The header is structurally the same screen: the “Order Information” H2, the RECT59 frame as a titled section, fields in layoutPlan (Y-then-X) order, and control kinds preserved — payment type as a RadioButtonGroup (not flattened to text), order-filled as a Checkbox, dates as DatePickers. Each construct shipped behind a Playwright + real-Oracle test plus a layout-fidelity gate. No TODO/FIXME markers exist anywhere in src/main/java.

The four silent losses

1

GLOBAL.customer_id calling-context contract

ORDERS can be launched already filtered to a customer (PRE-QUERY reads it, WHEN-CREATE-RECORD defaults a new order, PRE-FORM clears it). An entire cross-form interface — invisible in v2.

2

DATE_ORDERED $$date$$ default

A new order should default its ordered-date to today. Dropped.

3

QUANTITY_SHIPPED insert-only mode

updateAllowed=false, insertAllowed=true: editable while a line is new, read-only once saved. Flattened to plain editable.

4

SALES_REP_ID read-only deviation

v2 made it read-only — the right call — but nowhere recorded that this deviated from the spec’s “editable”. An undocumented right answer is still a hole: the next reviewer can’t tell it from an accident.

5

The confident false-absence claim

v2’s code carried a comment asserting “S_ORD has no WHEN-CREATE-RECORD” that nothing checked against the spec. It does have one. An invented absence made a silent drop look intentional.

§3 — Grill me: challenge the wins

The migrated parts are real, but the demo flatters them

3.1 “The PL/SQL migrated well” — true, but the demo is trivial

Confirmed by the source. The whole form is ~500 lines of PL/SQL, of which half is Oracle-generated master-detail boilerplate. Of the ~250 hand-written lines:

  • 34 of 45 triggers are trivial — a single built-in call, assignment, or SELECT-INTO.
  • ~8 are moderate — a SELECT-INTO + one branch + a NO_DATA_FOUND handler.
  • Exactly one hand-written trigger is “moderately complex” — and it’s deferred (the pick called form).
  • Zero packages, dynamic SQL, cursors over large sets, batch/FORALL, package state, savepoints, or differentiated error handling.

A real enterprise form has what this lacks: packaged domain logic (pricing, tax, credit limits, approvals in DB packages), dynamic query building (DEFAULT_WHERE), multi-error-accumulating validation, SQLERRM/SQLCODE handling, ON-INSERT/ON-UPDATE overrides, role checks, audit columns, RUN_PRODUCT reports.

Probes to actually challenge this
  • Migrate a form whose logic lives in a stateful DB package (a spec+body the AI must read) — does the “pure Domain method” translation hold, or does package state leak into the presenter?
  • Migrate a trigger with dynamic DEFAULT_WHERE query building — clean OrderSearchCriteria object, or string-concatenation hazard?
  • Migrate ON-INSERT/ON-UPDATE overrides — the whole-graph save() assumption breaks here.
  • A trigger that accumulates multiple validation errors before failing — Binder’s field-at-a-time model may not map.
  • A 500-line WHEN-BUTTON-PRESSED with nested loops and FORM_TRIGGER_FAILURE control flow — does fidelity survive, or does it silently simplify branches?

Hypothesis to test: the formulas migrate trivially at any scale; what breaks first in a real app is (a) packaged/stateful logic the boundary can’t hold, and (b) the volume of decision-prone properties overwhelming the ledger (→ §4).

3.2 “The layout looks ok” — true, but the view is ~1,158 lines

The layout is faithful, but it’s a single ~1,158-line view class mixing structure and all event wiring — fine on a demo, a maintainability cliff on a real form with 5× the fields.

Probes
  • Does fidelity survive multiple canvases / stacked windows / tab pages? The demo has one real canvas; CV_INVENTORY and CV_HELP were deferred — the hard multi-canvas case was never exercised.
  • Does layoutPlan ordering hold when frames overlap or nest, or with anchored positioning?
  • Does a form with 30+ header fields produce a usable FormLayout, or a wall?
  • Is the fidelity gate asserting grouping and order, or just presence? (Presence-only passes a scrambled-but-complete screen.)
§4 — Grill me: challenge the fix

Not missing features without knowing it

v3’s answer is the disposition ledger (ADR-0015): one row per form object plus one per decision-prone mapped property — every default, editability mode, visibility, value-propagation, cross-form contract. Every row must reach a disposition (migrated-as / re-decided / deferred / obsolete) before any build ticket is cut; to-issues refuses while a row is unassigned; each migrated-as row becomes a runtime acceptance criterion. Right shape, right grain — but unproven at scale, and never run.

The load-bearing question

Does the analyzer actually emit every decision-prone property automatically, or were the 151 rows hand-curated? If a human wrote them, the ledger only catches what that human already noticed — which is exactly the failure mode it claims to fix. The generator that produces the ledger from ORDERS.spec.json is the thing that should be under test.

More to grill
  • Row-count at real scale. 151 rows for a 34-item demo → plausibly thousands for a real module. Who assigns dispositions without rubber-stamping? What stops “assign all to migrated-as” becoming the new census?
  • “Decision-prone” is itself a judgment. The four losses looked mechanical too (a default, a flag). Who decides which properties get a row — and doesn’t that decision reintroduce the silent-loss risk one level up?
  • re-decided still needs a human to notice the deviation. SALES_REP_ID was caught by a retrofit audit, not the ledger. Would the ledger have flagged the spec-editable / built-read-only mismatch, or just provided a row to record it once someone spotted it?
  • The false-absence claim is only half-addressed. --check-refs verifies a cited ticket is live; it doesn’t verify a claim of absence against the spec. What catches the next invented “this form has no X”?
  • v3 was never built. Every “would have caught it” is a paper claim. The obvious next experiment: run the v3 build against ORDERS and confirm the four rows force the four features into existence.
§5 — Bottom line

Credible slice; the lesson is in how the misses were sorted

DimensionVerdict
PL/SQL fidelitygood Faithful — but the demo is trivial; unproven on packaged/stateful/dynamic logic (§3.1)
Architecture & concurrencygood The genuine engineering; solid
Layout fidelitygood Same screen — but single-canvas only, ~1,158-line view (§3.2)
Deferred surfacesgood Known and tracked — healthy
The four silent lossesgap Absent from v2, unknown to be absent — the core finding
The ledger fix (v3)unproven Right shape & grain, gates early — but never built, unproven at scale

The migrated app is a credible, well-architected slice whose business logic happens to be easy because the source is a textbook demo. The durable lesson isn’t in what was migrated — it’s in how the misses were classified: deferred-and-tracked is safe; the danger is the essential feature that has spec data, has a rule, renders as a correct-looking screen, and still never gets consumed — the loss nobody notices is gone.

The step that would actually settle it: build v3 and prove the ledger forces those four features to exist — then run the method on a form with real, packaged, stateful PL/SQL.
