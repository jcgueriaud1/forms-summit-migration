# migration-review

The build tickets (`ready-for-agent`, one per **construct**, produced by the
planner / `to-issues`) cover what an AFK agent can build. This skill covers what a
**human must own** — and emits it as first-class HITL tickets instead of leaving it
implicit. See `docs/adr/0014-hitl-review-tickets.md` for the decision and
`CONTEXT.md` for the vocabulary (_review ticket_, _out-of-slice surface_,
_generalization candidate_).

Every ticket produced here carries the **`ready-for-human`** triage label and opens
with the mandated disclaimer:

```
> *This was generated by AI during triage.*
```

## When to run

- After the planner has drafted the build tickets for a form (so the review tickets
  can reference them), or
- Per construct, right after it is built and validated against live Forms — while
  the seams are fresh.

The review tickets are a **sibling output** of the same spec + ruleset the build
tickets came from; they are not a second pass over the code.

## The three ticket types

All three are `ready-for-human` because each turns on a judgment the AI is not
entitled to make: *did it behave like Forms*, *defer or reject*, *generalizable or
specific*. Each derives from signals the method **already produced**, so the output
is grounded, not invented. Draft every candidate, present them to the maintainer,
act on the maintainer's decision, then publish.

### 1. Careful-review / manual-test ticket

**What it is:** the checklist of things a human must verify by driving the migrated
construct **side-by-side against the live Forms app** — the behavioural-parity and
layout-fidelity checks the AI cannot self-certify (it can make code compile and pass
unit tests; it cannot certify that the screen *behaves* and *reads* like Forms).

**Derive it from:**

- **Documented seams** (PLAN.md, the ADRs) — each is a place the new architecture
  deviates from Forms in a way that is correct but must be *seen*: Grid Pro commits
  per cell where Forms validated per item on navigation; `ORA_ROWSCN` optimistic
  locking is block-level, not row-level, without `ROWDEPENDENCIES` (conflict UX must
  be exercised); the spine flow (load → edit qty → swap product → add/delete line →
  totals recompute → commit under the SCN check).
- **The layout-fidelity gate** (ADR-0012, ADR-0013): a human confirms every in-scope
  item, frame, and heading renders in the form's order as its mapped component type —
  the silent-loss class behaviour tests sail past.
- **Ruleset outcomes that flagged themselves:** any construct whose classifier
  `treatment` is `Refactor` / `Unsupported`, or that hit an `escalate` (e.g.
  `image-item-file-sourced`, a custom `ImplementationClass`) — these are "no clean
  1:1, a human must judge the result".
- **Caution alerts / business rules** the spec surfaces (e.g. `PAYMENT_TYPE_ALERT`,
  "This customer must pay cash!") — confirm the rule still fires and reads right.

**Ticket body:** use the [careful-review template](TICKET-TEMPLATES.md#careful-review).
State *what* to test, *why the AI can't self-certify it*, the concrete side-by-side
checks, and links to the build ticket(s) it reviews.

### 2. Out-of-slice / deferred follow-up ticket (or PRD)

**What it is:** the form's dependencies that are **in scope for the eventual
migration but deferred out of this slice** — surfaced so they become *tracked
forward work*, never a silent drop.

> **This is a distinct lane from `.out-of-scope/`.** `.out-of-scope/` records
> *rejected* features (see `triage/OUT-OF-SCOPE.md`). A deferred surface is *accepted
> but not now*. The human makes the **defer-vs-reject** call per surface.

**Derive it from:**

- The spec's `## Dependencies (out-of-slice surfaces — decide per item)` section —
  each row is `status: undecided` by construction (the analyzer never decides). For
  ORDERS that is `menu-module m_summit`, `called-form pick`, `attached-library
  CALENDAR`, `object-library CALENDAR`.
- `Unsupported`-target items that are not part of the current slice.
- Referenced program units / sibling forms the slice does not implement.

**Flow per surface — the human decides:**

- **Defer** → draft a follow-up **issue** with `to-issues` (a bounded surface, e.g.
  "attach the CALENDAR date-LOV") or a **PRD** with `to-prd` (a whole feature, e.g.
  the `pick` product-picker form). Publish `ready-for-human` (or `ready-for-agent` if
  the maintainer judges it fully specified).
- **Reject** → route to the existing rejection lane: write to `.out-of-scope/` and
  close, per `triage/OUT-OF-SCOPE.md`.

**Ticket body:** [deferred-surface template](TICKET-TEMPLATES.md#deferred-surface).

### 3. Generalization-review ticket

**What it is:** the PLAN.md generalizable-vs-specific sort applied **proactively at
design time**. The ruleset derives some constructs *into a form's view* that are
really **generic Oracle Forms affordances** — they belong in a **reusable layer**,
not baked into `OrdersView`. This ticket lists those candidates and recommends the
extraction; a human makes the final call.

**Derive it from — generic-by-construction outputs:**

- **Record actions** from `blockActionClassifiers` — Delete / Duplicate / New come
  from *any* database block's `crud` capability, not from anything specific to this
  form. → a reusable block-actions component, parameterised by the block's CRUD +
  relation delete policy.
- **The filter bar** (Execute Query / Enter Query → persistent filter + lazy paged
  DataProvider) — the generic replacement for QBE mode, identical shape for every
  master block.
- **The `ORA_ROWSCN` optimistic-lock commit path** — generic transaction/locking
  infrastructure, not order logic.
- **The `CLIENT_IDENTIFIER` audit bridge** — generic connection/identity plumbing.
- **Confirm-on-destructive-action** dialog — a generic pattern, not a form feature.

**The bar for "generalize" (PLAN.md):** a candidate earns it only when the rule can
be **stated in form-construct terms** ("*any* deletable database block gets a
relation-policy-aware Delete action"). If it can't be so stated, it is **specific by
default** — say so and leave it in the view. The ticket *recommends*; the human
decides, and it stays HITL precisely because this judgment is the thesis of the POC.

**Ticket body:** [generalization template](TICKET-TEMPLATES.md#generalization). For
each candidate: the generic layer to extract into, the form-construct-terms
justification, and the explicit specific-by-default caveat.

> **Not this skill's job:** actually building the reusable layer. The ticket
> recommends the extraction; once a human approves, an agent builds it from that
> ticket.

## Output & relationship to the scorecard

- The **careful-review** results feed the scorecard's *Behavioral parity* column.
- The **generalization** decisions feed the *generalized-into-skill vs
  stayed-specific* split — the ratio that is the POC's headline number. A candidate
  the maintainer approves for the generic layer is a generalizable fix captured
  *before* it was ever hand-fixed in the view.
- **Deferred** surfaces become tracked tickets/PRDs, keeping the "nothing dropped
  silently" guarantee honest at the slice boundary.

## Composition

- Reuses `to-issues` and `to-prd` templates for deferred follow-ups — this skill does
  not reinvent them.
- Publishes through the same issue tracker and label vocabulary as `triage` (run
  `/setup-matt-pocock-skills` if the tracker/labels were not provided).
- Does **not** modify the planner, the build tickets, or `migration-rules.yaml`.
