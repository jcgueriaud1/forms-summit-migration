# Review ticket templates

Bodies for the three HITL ticket types emitted by `migration-review`. Every ticket
is published with the **`ready-for-human`** label and opens with:

```
> *This was generated by AI during triage.*
```

Keep bodies durable per `triage/AGENT-BRIEF.md`: describe behaviour and contracts,
not file paths or line numbers.

---

## Careful-review

```markdown
> *This was generated by AI during triage.*

## Construct under review

Which construct this reviews (name it in Forms terms) and the build ticket(s) it
follows — e.g. "Detail block inline editing (#NN)".

## Why a human must certify this

The AI compiled it and unit-tested the formula; it cannot certify that the construct
*behaves* and *reads* like Forms. This is behavioural parity + layout fidelity.

## What to test side-by-side against live Forms

- [ ] Seam: <the deviation> behaves acceptably — e.g. Grid Pro commits per cell where
      Forms validated per item; confirm no data is lost / no surprising re-entry.
- [ ] Optimistic-lock conflict path: force a concurrent edit; confirm the SCN check
      rejects and the UX is clear (block-level SCN, no ROWDEPENDENCIES).
- [ ] Spine flow end-to-end matches Forms.
- [ ] Layout-fidelity gate: every in-scope item, frame, and heading renders, in the
      form's order, as its mapped component type (ADR-0012 / ADR-0013).
- [ ] Business rule / caution alert still fires and reads correctly.

## Notes

Ruleset flags that routed this here (Refactor / Unsupported / escalate), if any.
```

## Deferred-surface

```markdown
> *This was generated by AI during triage.*

## Out-of-slice surface

The dependency, named as the spec records it (type · name · via) — e.g.
"called-form `pick` (CALL_FORM/OPEN_FORM)". This is **accepted but deferred**, not
rejected.

## Decision needed from a human

**Defer** (tracked forward work) or **reject** (out of scope)?

- Defer, bounded → a follow-up **issue** (drafted with `to-issues`).
- Defer, whole feature → a **PRD** (drafted with `to-prd`).
- Reject → write to `.out-of-scope/` and close (`triage/OUT-OF-SCOPE.md`).

## What it provides in Forms

One or two sentences on the capability the surface delivers, so the defer/reject call
is informed.

## Draft follow-up (if deferred)

The `to-issues` / `to-prd` body, ready to publish once the maintainer says "defer".
```

## Generalization

```markdown
> *This was generated by AI during triage.*

## Candidate to generalize

The construct the ruleset put in the form's view that looks generic — e.g. "the
Delete / Duplicate / New record actions derived from the block's CRUD capability".

## Proposed generic layer

Where it should live instead of the form view (name the reusable component / service),
and how it is parameterised (e.g. by the block's CRUD flags + relation delete policy).

## Justification in form-construct terms

The rule, stated so it applies to **any** form — the PLAN.md bar for "generalizable":
"*any* deletable database block gets a relation-policy-aware Delete action".

## The call is the human's — specific by default

If the rule above cannot be stated in form-construct terms, this stays **specific**
and lives in the view. Recommend, don't decide. Approved candidates feed the
scorecard's generalized-vs-specific ratio.
```
